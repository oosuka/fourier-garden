- 全周期dry stereo RMSの比較基準は0.023 ±0.05 dB。マスターのピーク上限は音響正本で確認する。
- scene、AudioNode、AudioContext、rAF、購読、タイマーを所有者が破棄し、古い世代の通知を混入させない。
- strict TypeScript、Oxlint、Biomeを維持する。型アサーションや規則無効化で失敗を隠さない。

## 4. Lunaでの実行規律

- 一度に一つの作業IDを扱う。通常は1章・1renderer、または再現した不具合1件。
- 一つのカードで読む実装は、対象章と直接呼ぶ共有コードに限定する。全リポジトリを毎回読み直さない。
- 最初に「期待する挙動」「見る場所」「成功条件」を短く決めてから操作・修正する。
- 修正が必要なら別の `FIX-001` などへ切り出し、発見元のカードと結ぶ。
  まず再現、原因の確認、最小修正、対象を再検証。同じ症状へ根拠のない値変更を重ねない。
- 数学・DSP・時計・寿命の修正は、一つの不変条件に絞ってxhighで扱う。
  2つの独立した正解根拠を用意する。例：解析式と境界の数値、参照DSPとWorklet実波形。
- 2回の仮説検証で進展しなければ、同じ測定を繰り返さず、反証と未確定点を記録してさらに小さく切る。
  不明な値を推測して変更しない。重大な実行時不具合は未解決のまま完成扱いにしない。
- 問題のない共通部へ予防的改造を広げない。見た目の好みだけの変更は、具体的な比較と効果がある場合に限る。
- 挙動のバグには修正前に失敗する意味のある回帰テストを置く。
  低影響の数式改行・文書整形へ、実装文字列をなぞるだけのテストを増やさない。
- 関連テストを先に通す。全体checkは依存する修正のまとまりの終了時と最終版で実施する。
  ファイルを読んだだけ、タブを失っただけ、記録を追加しただけで全テストをやり直さない。
- 音響変更時はTypeScriptと `public/audio/` を同時に検証し、音響性能と決定的レンダー比較を行う。
- 検証済み項目は、依存するコードや条件が変わった時だけ再検証する。
  日付が古いという理由だけで、変更に無関係な証拠まで無効にしない。
- 60秒を超えて利用者を無言にしない。ただし性能記録中はブラウザを触らず、記録前後に説明する。
- 通常の修正・検証について承認待ちを作らない。追加の利用者試聴を完了条件にしない。

### P：1章・1rendererの4K 60秒

推論：high。実装変更なしで測るカード。手順は後述の「静かな60秒計測」。

- CSS／実ラスタ3840×2160、DPR 1、high、通常motion、48 kHz、音量35%、ノート閉、前景。
- 起動・shader準備・seek直後を避け、通常後処理で60秒記録し、JSONを保存。
- 平均fps、CPU送出p95、間隔p95／最大、50 ms超件数、slowFrames、同期差、開始終了絶対時刻を読む。
- 60 fpsは目標。59.9998のような時計丸め相当の差を性能バグにせず、フレーム数・欠落も見る。
- 長い欠落があれば、前景・他処理・観測干渉を確認する。原因仮説を立てた比較を1回追加し、
  再現する問題を `FIX` へ切り出す。合格が出るまで無制限に撮り直さない。
- `post=direct` は診断用。これだけの成功を通常設定の成功へ置き換えない。

完了条件：現行対象版の有効なJSON、条件と解釈があり、説明できない再現性のある性能問題が残っていない。
既存のCathedral／MöbiusのPカードは、描画・音声経路が変わっていなければ再利用する。

### T：1章・1rendererの時間演出、局所因果、高DPI、連続動作

推論：high。疑義の原因分析はxhigh。1カードにつき連続10分を今回の確認窓とする。
これは無期限の安定性の証明ではなく、全章共通の有限な検証条件である。

1. 章の幕境界・スコア周期をソースから読み、観察する絶対時刻を先に記録する。
2. DPR 2を実環境で確認し、通常motionで前景のまま連続再生する。通常のviewport overrideはDPR 1になり得る。
   指定のDPRを設定できない場合は、実値を記録し、DPR 2確認済みにしない。
3. 全5幕、少なくとも2周回、局所的な発音の立ち上がりと尾、章固有の材質・運動を観察。
   静止画の差だけで5幕の動的品質を判断しない。利用可能なら短い局所動画を保存し、巨大な録画は残さない。
4. 高DPIの静かな60秒計測を序盤と終盤に一つずつ取り、同期推定差の持続的な増大、欠落を比較。
   計測中はDOM／AX／画像を読まない。5幕の観察は計測外の時間にも行う。
5. 同期をsourceIndex、絶対イベント時刻、有限包絡、位置／pan、局所利得から照合する。
   音だけ・映像だけ・同時の評価を別欄へ記載し、実際に観察できなかった知覚的項目を偽って埋めない。
6. 連続窓の終了後にpause/resume、長い絶対時刻へのseek、逆seek、周回境界を確認。
   10,000秒へseekできた事実を、10,000秒の連続再生と呼ばない。

完了条件：高DPIの実条件、全幕の記録、連続窓の長さ、開始・終盤の計測、局所因果の根拠、限界が揃う。
装飾差・明るさ差だけでは章の個性が弱い場合、具体的な局所改善を `FIX` に分ける。

- 主張を「厳密式」「有限計算」「音への変換」「詩的造形」に分ける。
- 境界、符号、係数、周波数、位相、絶対時刻、サンプル解像度と別名を照合する。
- 既存の解析・境界テストと小さい独立数値計算を根拠にする。テストと実装の同じ誤式を正解にしない。
- 実験の説明が本編の音や形を直接変更すると誤解させていないか確認する。
- 誤りがなければ変更しない。誤りがあれば回帰と正本・実装・説明を同じカード由来の `FIX` で揃える。

完了条件：章の主要主張から実装・検証への参照があり、数式の食い違い・過剰な主張が解消されている。

- 利用可能な `mcp__cua_repl.js` を使い、初回の入口と返されたAPI文書に従う。

### 静かな60秒計測

観測操作自体がフレーム欠落を発生させた履歴がある。
開始直後のAX取得で0.45秒付近、58秒後のAX取得で58.48秒付近に長い間隔が生じ、
終了まで読まない試行は0回だった。これをすべての過去の欠落の原因と断定はしない。

1. 画面寸法、再生、QA展開、ノート閉を準備し、状態を確認する。必要なら先にseekする。
2. 記録前に利用者へ短く説明する。
3. 「60秒を記録」をクリックした後は、60秒間、DOM／AX／画像を取得しない。
   build、テスト、他タブ、ソース編集も同時実行しない。
4. 使用中のAPIが対応する場合、クリックと `waitForTimeout(60000)` と終了後の状態取得を一回の呼び出しへまとめる。
   呼び出しtimeoutは65秒程度、実際のwaitは60秒以下。API文書にない待機方法を推測しない。
5. 500 msの表示更新のため終了直前の表示が残る場合がある。「JSONを保存」の出現を待って保存する。
6. JSONの章、renderer、寸法、開始終了時刻、statusを確認し、直ちに `docs/qa/renewal/` へ別名保存。
   `interrupted` を成功として使わない。ファイルを失った試行には結果を捏造しない。
7. レポートを回収してからpauseや詳細操作を行う。

ダウンロード名は `fourier-<chapter>-<timestamp>.json`。
ダウンロードフォルダーからコピーする場合は、章と `firstScoreSeconds` など実際のレポート内容で対応を確定する。
「最新ファイル」という理由だけで別試行を取り込まない。過去のダウンロードを削除しない。
保存名の例は `luna-wavelet-rain-webgpu-4k-01.json`。再試行は連番を変え、元データを保持する。

画像は実際に保存できたものだけをリンクする。タスク内画像だけならその旨を記録する。
スクリーンショットは動き・音色・知覚同期の証拠ではない。
